# GuideRail 产品复盘：先解决反复出现的不便

记录日期：2026-09-05。适用范围：GuideRail 后续规划，以及类似个人效率工具的需求判断。

## 最初的问题与范围偏移

用户的真实困扰是：ChatGPT 对话很长，有价值的回复被淹没，之后难以找回和复用。

早期方案逐步加入项目、计划、阶段、步骤状态、问题分支和执行引导。每个功能单独看都能解释用途，但组合后变成了任务管理系统。用户为了保存和找回一段回复，反而要理解、建立和维护额外结构。

这是本项目的过度开发：在尚未证明用户需要任务管理之前，就围绕设想扩展了产品。AI 助手也推动了这种偏移，过早把一个具体不便转化为完整系统设计。实现速度快，不能替代需求成立的证据。

## 回到完整的使用故事

用户与 ChatGPT 多轮讨论本地 AI 部署，得到满意的步骤后收藏回复；第二天从侧栏找回方案，遇到问题就定位回原回复继续追问；部署完成后，将最终方案导出到 Obsidian，补充自己的实践记录。

这个过程需要的是：

| 用户要完成的事 | 当前能力 |
| --- | --- |
| 先留住有用的回答 | 一键收藏 |
| 之后读到保存的内容 | 收藏列表与原文阅读 |
| 回到上下文继续讨论 | 定位原回复 |
| 留作长期笔记 | 导出 Markdown，附 YAML 来源与时间等元数据 |

这已经构成当前需求的完整流程。Obsidian 导出也遵循同一原则：选择仓库内文件夹并生成合适格式即可，不因为目标是 Obsidian 就自然扩展出专用插件、服务或同步系统。

## 后续开发准则

1. **先证明不便反复发生，再增加功能。** 用户实际遇到的阻碍是依据；“以后可能有用”先记入需求文档，不直接开发。
2. **先讲使用故事，再列功能。** 说清谁在什么情境下做什么、哪里受阻，以及完成的标志。无法放进真实流程的功能暂缓。
3. **优先减少用户动作。** 新增结构如果需要用户持续维护，必须证明它带来的收益足以抵消负担。
4. **从最小完整流程开始。** 收藏、找回、定位、导出能把用户的事情办完，就先停止扩展，实际使用后再判断缺口。
5. **把可靠性放在功能数量之前。** 优先处理收藏失败、定位不准、正文缺失、导出格式错误及文件保护问题。
6. **区分代码完成与体验验证。** 自动测试通过说明部分实现符合预期，不能代替用户在 Chrome 和 Obsidian 中的实际验收。

新增需求时只需写清四点：实际场景、发生频率、现有方法为何不足、最小改动及验收结果。信息不足就保留为候选，不必先设计整套系统。

## 当前决策

以“收藏 → 找回原文 → 导出笔记”为当前产品边界，先实际使用一至两周，再根据反复发生的问题决定下一步。早期任务管理规划作为历史保留，不自动恢复推进；也不为追求代码整洁立即重写或删除兼容逻辑。

“目前够用”是基于当前使用故事的判断，不代表已经证明适合所有用户，也不意味着永远不增加功能。后续范围变化应由新的实际需求驱动。
